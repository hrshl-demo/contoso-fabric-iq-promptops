# Customer request handling and status (SOP-SHARED-REQUEST-HANDLING)

Synthetic Contoso demo procedure - fictional internal policy, not legal or regulatory authority.

**Applies to:** all cases   **Scope:** shared   **Source version:** 1

## Purpose
This procedure defines the meaning of customer request statuses and the circumstances in which a status may be changed, so that staff use consistent wording and reflect only recorded events in the case record.

## 1. Scope and policy context

This is a Synthetic Contoso demo procedure - fictional internal policy, not legal or regulatory authority.
Apply this procedure whenever staff record, review or communicate the status of a customer request.

## 2. Core status handling rule

Every status shown on a customer request must reflect the case record. Do not change a status unless the change is supported by an actual recorded event.
Use status language carefully and consistently so that the status describes the present stage of handling, not an assumption about progress.

- Treat a request as registered when it has been logged in the record.
- Use awaiting response when further input, clarification or action is pending from the relevant party.
- Use resolved only on a real event.

## 3. Communication standards

When updating notes or communicating with a customer, describe the request exactly as supported by the record.
An application must never be described as approved unless there is a reviewer event recorded for that application.

- Do not present submission as resolution.
- Do not present an acknowledgement as completion.

## 4. Verification before status change

Before any status change, review the case record and confirm the event that supports the new status.
If the record does not show the required event, keep the current status unchanged until the record is updated appropriately.

## 5. Stop and escalate

Stop processing the status change immediately if no recorded event supports the status.
Refer the matter for human review where the wording to be used or the authorisation basis is unclear.

## Required checks
- Confirm that a status change is backed by an actual recorded event.
- Confirm that an application is never described as approved without a reviewer event.

## Prohibited assumptions
- Do not assume that submitting is resolving.
- Do not assume that an acknowledgement is a completion.

## Stop conditions
- Stop if no recorded event supports the status.

## Valid outcomes
- registered
- awaiting response
- resolved only on a real event

## Human gate
Only a human reviewer may authorise any status wording that states or implies approval.
