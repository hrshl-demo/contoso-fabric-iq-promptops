# Changelog

Newest first. Every prompt version has one line of the form `` - `<prompt id>` <version>: <what changed> ``; `python -m tools.lint_prompts` checks it. A release turns `## Unreleased` into `## vX.Y.Z — YYYY-MM-DD` (`python -m tools.release prepare`, see `docs/RELEASING.md`); `python -m tools.release lint` checks the structure.

### Pipelines
- Release: `release` workflow (run by hand from the Actions tab) checks the rules, rebuilds the files from the commit, and publishes a GitHub release with the Monthly Business Brief, the ontology brief, the Fabric item definitions, the prompt library and checksums. A dry run is the default. CI builds the same files on every pull request (`release-preview` artifact). Optional **Deploy to prod** (with Publish) deploys only what the last dev deployment that really ran had (a run whose deploy job was skipped does not count) and always loads the data again.
- Deployment (draft, off until `CD_ENABLED` is set, see `docs/SETUP.md`): `cd-dev` deploys to the dev workspace after a merge that changes what is deployed; `capacity` gives status, resume, pause and a guard every 3 hours that pauses a forgotten F4 (a demo hold variable stops it). `tools/cd.py` runs the steps, stops them at a deadline, checks the workspace is on the capacity it pauses, and always pauses the capacity once it has been resumed, also after a failure; it is tested with fakes and against the kit's Fabric mock, not yet against a live tenant. The capacity role needs `write` as well as read, suspend and resume (Microsoft's pause and resume page) and is assigned on the capacity itself.
- Plans: `docs/SETUP.md` (the one-time identity, role, Fabric settings and first runs, each step marked as needing your go) and `docs/PILOT.md` (shortcut and Databricks pilot, costs and decision rules; not started).
- Platform, onboarding of the content repository, 4 Nov 2026: the first `build` after `bootstrap consumer` failed before the F4 ever ran, because Azure refuses to update a paused capacity (*Service is not ready to be updated*) and the build tried to add the new administrator before it resumed the capacity. An update now resumes a paused capacity first (the test fake models Azure's refusal, so the old order fails its test); the build had been re-run with the capacity resumed by hand in the meantime.
- Platform and ontology, 4 Nov 2026 (second live stretch): the ontology gate opened less than 5 minutes after a capacity admin switched on the two capacity-level settings (clicked about 11:05, the pipeline's probe found it open at about 11:10 and created and deleted an empty ontology), and the first live `cd-dev` deploy then worked end to end in about 11 minutes: semantic model `ContosoBankModel` (32 tables, 36 relationships, 39 measures), ontology `ContosoBankOntology` (31 entities, 53 relationships, 23 rules), graph refreshed and queryable (31 node types, 53 edge types), and the ontology's MCP endpoint answering with three tools. The data was loaded once more because no earlier dev deployment was known. F4 time for the whole day: about 90 minutes, about USD 1.1 at the list price, most of it waiting for the capacity click.
- Platform, first live run, 4 Nov 2026: the build ran to the end of the data load (exit 3, the ontology gate is closed). Three things no fake could show were fixed on the way (a subscription policy closed the storage account to GitHub's runners, so `CD_DATA_SOURCE` defaults to the repository; Fabric quota 0 in East US 2, so `bootstrap apply` reads the quota first and `CD_LOCATION=centralus`; the second Fabric tenant setting was not effective, so `check` proves the workspace-creation door with an empty probe workspace). A workspace made by hand with the pipeline's identity as Admin is the supported way round a tenant that does not let service principals create workspaces (`check` then shows that door as *not needed*). Measured: 63 tables load in about 4 minutes; capacity active 2 minutes after the dispatch; about 8 minutes and about USD 0.07 of F4 from start to pause. With `gate_wait_min` 0 the request now says plainly that the run does not wait and that the click is for a later run (a paused capacity greys the settings out).
- Platform (draft; first live run on 4 Nov 2026, see the entry above): the `platform` workflow builds everything from blank. `tools/platform.py` builds the layers offline from the seed data in the repository (`CD_DATA_SOURCE=repository`, the default; with `storage` it goes through a storage account in `infra/main.bicep`, with CI compile and lint, which the first live run showed a subscription policy can close to GitHub's runners), creates the F4 (or keeps the one that exists: never resized, never loses an administrator; a person is a capacity administrator by user principal name, a service principal by object id), the workspace and the lakehouse, loads the data, checks the ontology gate and asks a capacity admin to open it while the data loads, and pauses the F4 (also after a failure, an interrupt or a deadline; a capacity deployment still running behind the pause is cancelled and waited for first). `check` is free and read-only and runs before every build; `build` and `destroy` need a typed confirmation, an approver and `main`; `destroy` purges the workspace like the kit's wipe and pauses what it resumed. The last line of defence is `tools.platform rescue`, preceded by a fresh sign-in (an OIDC sign-in lasts about an hour). The capacity guard treats a capacity that does not exist yet as nothing to guard. A cancelled capacity deployment is not trusted to be an undo: the pause waits for a capacity that is still being provisioned and looks for one that appears late; whenever a deployment was in doubt and nothing proves that no capacity will appear, or the capacity is paused but its deployment is not over, the run ends in exit 4; an unreadable capacity size or administrator list is refused. `tools/bootstrap.py` scripts the one-time identity (an empty resource group, the app and its main-branch-only trust, an Entra group for the Fabric tenant settings, roles on that resource group only, the repository secrets and variables) as a dry run by default, refuses first, read-only, anything that looks like a mistake (a repository that does not exist, a resource group that is not empty, an app with any federated credential besides the one it is for, a role with the consumer role's name that is not the role this project defines), and onboards a content repository with a least-privilege role on the capacity itself.
