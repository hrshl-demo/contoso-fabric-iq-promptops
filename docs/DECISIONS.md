# Decisions

Dated 3 November 2026. Evidence is from Microsoft Learn and the Microsoft skills repo as of that date; the ontology and graph features are in preview and change often.

## Made

| # | Decision | Why | Revisit when |
|---|---|---|---|
| D0 | **The F4 capacity region is a setting (`CD_LOCATION`); the demo subscription uses Central US, the code default stays East US 2** *(revised 4 Nov 2026)* | East US 2 is the kit default, the ontology agent needs no cross-geo setting in the US or EU, and F4 costs USD 0.72/h there (Australia East 0.84, Central India 0.80, South India 0.88). **The demo subscription has a Fabric quota of 0 capacity units in East US 2** (also East US, West US, South Central US, North and West Europe, UK South, Canada Central) and 512 in Central US, North Central US, West Central US, West US 2 and 3, Australia East, Central and South India, Southeast and East Asia, Japan East and others, found when the first F4 deployment was refused (4 Nov 2026, nothing created). Central US is a US region (no cross-geo setting) at the same price. `bootstrap apply` now refuses a region without quota, read-only, before anything is created, and names regions with room. India South Central has no Fabric capacities. The build VM size is restricted in Australia East | A region is chosen for latency or residency, or the quota in East US 2 is raised |
| D1 | **Private repo on GitHub Free**, with a manual-approval workflow in front of production | Required reviewers, wait timers and environments on a private repo need GitHub Enterprise Cloud, which a personal account cannot buy. Free keeps cost at zero. Branch protection and rulesets are not available either, so the PR-only rule lives in `AGENTS.md`, `CODEOWNERS` and the pipeline | You move to Pro (environments, branch protection), an organisation, or a public repo |
| D2 | **Pilot ADLS Gen2 shortcuts first, then decide where the medallion lives.** Databricks is tried only if that pilot passes. Fabric-native managed tables stay the proven fallback | See the evidence below: the docs disagree on whether the ontology binds to shortcut tables | The pilot finishes (plan and costs: [PILOT.md](PILOT.md)) |
| D3 | **OIDC service principal on GitHub-hosted runners** for CI/CD. The federated credential trusts runs on `main` only. Fallback: a self-hosted runner on the VM `host` signed in as the demo admin | Passwordless and the standard story. The pipelines are written and tested with fakes; whether a service principal may create ontology (preview) items is not yet proven. The role scope is refined by D8 | The first live run, or the spike shows the service principal cannot create ontology or graph items |
| D7 | **Two parts.** Part 1 (this repository): one pipeline builds the platform from blank, from the data source to a loaded lakehouse. Part 2 (a separate repository): prompts, ontology and reports with their own CI/CD, deploying into the platform's workspace ([CONSUMING.md](CONSUMING.md)) | The user's direction on 3 Nov 2026: everything through CI/CD, with the content versioned in its own repository so the demo shows prompt and report versioning | Part 2 is built |
| D8 | **The identity bootstrap is the one scripted manual step** (`tools/bootstrap.py`): it creates an **empty** resource group (and refuses an existing one that is not empty and not made by this project), the pipeline's app and federated credential (and refuses an app that trusts anything besides this repository's main branch, whatever the other credentials are called), an Entra group for the two Fabric tenant settings, and **Contributor and Storage Blob Data Contributor on that resource group only**. It cannot be done by the pipeline itself (nothing exists to sign in with yet). A content repository gets a custom role limited to a capacity (Azure needs `write` for pause and resume) **assigned on the capacity itself**, so it can run that capacity and cannot create another | Creating resource groups would need rights on the whole subscription; the pipeline must create the capacity, so pause-only rights are no longer enough. Everything that can be refused is checked read-only first, in the dry run too. Dry run by default, `--subscription` required to execute, idempotent. A role on the capacity disappears with it, so a rebuilt capacity needs `bootstrap consumer` again | A tenant policy blocks the app or the group, or the rights prove too wide |
| D9 | **The seed data reaches the lakehouse as managed Delta tables, built offline from the seed in the repository (`CD_DATA_SOURCE=repository`, the default) or, opt-in, through an ADLS Gen2 storage account (`storage`)**. No shortcut and no Databricks in the platform. *Revised on 4 Nov 2026 after the first live run: the storage account was the original default (3 Nov, chosen while the user was away)* | The user's earlier decisions: blob if Databricks costs too much, and Fabric-native tables as the fallback. Managed tables are the proven path for the ontology (see D2). The first live run showed that the demo subscription's governance turns off public network access on a new storage account, so GitHub-hosted runners cannot upload to it; the run failed at that step, before the capacity existed, and nothing billed. A pipeline must not override a tenant's network policy, so the default no longer needs a storage account. Shortcuts and Databricks stay a pilot ([PILOT.md](PILOT.md)) | The user wants the storage account back (a self-hosted runner or a private endpoint, or a policy exemption from the tenant owner), or the pilot passes |
| D10 | **The ontology gate is checked right after the workspace exists, and the admin is asked then**, while the data loads | The admin's capacity setting needs 7 to 11 minutes to apply, about the time the load takes, so the two overlap and the F4 runs less. A paused capacity greys the setting out, so it is asked for while the capacity runs | The first live run shows the settings apply faster or slower |
| D11 | **An existing capacity is never resized and never loses an administrator; capacity administrators are a UPN for a person and an object id for a service principal** | Found by the independent review. An ARM deployment of a capacity that exists is an update: a re-run would have forced an F8 back to F4 (a bill change, and the kit's own rule is never to resize) and replaced the administrator list. And Fabric takes a UPN for a user (the azurerm provider's docs for the same API version say so) where the first draft passed object ids. The build now reads the capacity first and deploys only what is missing | A live run shows Fabric accepts object ids for users too |
| D12 | **Before a pause is owed, a capacity deployment that may still be running is cancelled and waited for; a cancel is not trusted to be an undo (a capacity still being provisioned is waited for and one that may appear late is looked for; whenever a deployment was in doubt and the run cannot prove nothing will appear, or the capacity is paused but its deployment is not over, it is exit 4); the last line of defence is `tools.platform rescue`; `destroy` resumes only to purge and always pauses** | Found by the independent reviews: a cancelled or abandoned run leaves the ARM deployment going, and it can create a *running* capacity just after the pause looked and found nothing; after the first fix a `Running`, `Unknown` or `Canceled` deployment with no capacity yet was still reported as "nothing to pause", and after the second a warning was still a green exit although the capacity service can finish what it had started. Only Azure's own "not found" counts as "no such deployment": a sign-in or network failure does not. The user's one rule is that nothing bills unseen. A deployment cancelled by anyone (a person in the portal, an earlier run) less than 30 minutes ago counts as in doubt too; an older cancelled record does not, so it cannot turn every later destroy red. The cost of the stricter rule is a red run in the abnormal cases only (a cancelled or timed-out capacity deployment) | The first live runs show how long a capacity deployment, a cancel and a late appearance really take |
| D13 | **Creating workspaces is proven by `check` with an empty probe workspace (no capacity), deleted at once** *(revised 4 Nov 2026; the first draft did not probe it)* | The first draft did not probe it, because Fabric's Create Workspace also wants the caller to administer a capacity and none exists before the first build. The first live run showed that the refusal for a closed tenant setting is a 401, and it came at step 8 with the F4 already running (about 2 minutes, a few cents). A workspace without a capacity needs only the tenant setting, so the free `check` can prove the second door too, and a closed door stops a `build` before anything is created. Any other answer is reported as skipped, never as closed | Fabric starts refusing capacity-less workspaces for service principals |
| D14 | **A managed app trusts exactly one subject, and a role is trusted by its definition, not its name; an unreadable capacity size or administrator list and a gate probe that cannot clean up are refusals, not shrugs** | Found by the second and third independent reviews. A federated credential under any name other than `github-main` kept another repository's right to sign in as the pipeline's identity (Contributor on the resource group), and one with the right subject but another audience would have been taken for the real trust; a pre-existing role with the consumer role's name but broader actions, a condition or split permission blocks would have been assigned; an unreadable administrator list became an update that deployed only the configured members, and an unreadable size could have been resized by it; a probe that could not be removed still gave a green build and could keep the capacity running. All are now refused (the first two read-only, before any change, in the dry run too) | A deliberate second credential or a shared role is wanted: it needs its own decision |
| D15 | **A policy that closes a resource to the pipeline is obeyed, not worked around; the pipeline says so and uses a path that does not need the resource** | Found by the first live run (4 Nov 2026, 02:27): Azure created the storage account with public network access *disabled* (the template does not ask for that; the subscription's governance does), and the CLI's generic 403 text blamed "network rules". Re-enabling it, or asking for a policy exemption, would override a tenant's security control, which is the tenant owner's decision. The upload failed before the capacity existed, so it cost nothing. See D9 for the new default; the error text of a refused upload now names the cause and the variable to set | The tenant owner allows it (an exemption), or a private endpoint with a self-hosted runner is set up |

Defaults assumed, change by pull request: repo `hrshl-demo/contoso-fabric-iq-promptops`; reports are Power BI PBIR plus PDF/PNG exports; the F4 is paused, not wiped, between sessions; the skills bundle is pinned in `skills.lock`.

## Evidence behind D2

- The new (Gen 2) ontology is TMDL with Direct Lake partitions over a lakehouse SQL endpoint. The kit already emits it (`kit/contoso_onto/oac.py`).
- Learn, *What is ontology (preview)?* (16 Oct): binding sources include lakehouses, warehouses, SQL databases, mirrored databases and "supported OneLake constructs such as shortcuts, views, and materialized views". Learn, *Bind data* (21 Oct) lists lakehouse, mirrored database, semantic model, SQL database, warehouse, eventhouse and KQL database.
- Learn, *Materialize an ontology graph* (29 Sep): graph accepts "only delta tables from lakehouses or mirrored databases"; entities with several backing tables or semantic-model bindings are not eligible.
- Against: Learn, *Troubleshoot ontology* (1 Oct) and the skills repo say ontology supports **managed** lakehouse tables only, not external tables shown in the lakehouse. The skill documents the older JSON format; the old experience retires on 31 Jan 2027.
- Databricks routes: an ADLS Gen2 shortcut to Delta files, or a mirrored Azure Databricks catalog (Unity Catalog with external data access, `EXTERNAL USE SCHEMA` and `SELECT`; creates a mirrored item, a SQL endpoint and shortcuts; read-only).

## Never without an explicit go

Create or resume a capacity, start a VM, create storage or Databricks, create the Entra app (`tools.bootstrap --execute`), run the `platform` workflow with `build` or `destroy`, change a tenant-wide Fabric setting, merge or push to `main`, wipe.
