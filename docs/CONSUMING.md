# Consuming the platform: the contract for a content repository

The platform ([PLATFORM.md](PLATFORM.md)) gives you a **running-on-demand Fabric workspace with a loaded lakehouse**. A content repository (ontology, semantic model, reports and their prompts) deploys into it through its own CI/CD. This page is what the platform promises and what it asks of you.

## What you get

| Promise | Value |
|---|---|
| A resource group, a capacity, and a workspace for dev and one for prod | Names are repository variables of the content repository (below). The capacity is an **F4 that is paused** unless something is running |
| A lakehouse named `ContosoBankLH` in the workspace | With the **core tier: 32 gold tables** (the full tier has 51). Managed Delta tables, so the ontology can bind to them |
| A SQL analytics endpoint on that lakehouse | Direct Lake semantic models and the ontology bind through it |
| Your identity is a **capacity administrator** and a **workspace Contributor** | After you are onboarded and the platform has been built once more |
| The ontology gate is open | `platform-outputs.json` says `ontologyGate.status` is `open`. If it says `closed` the platform asked an admin to open it |
| Synthetic data only | Nothing in the lakehouse is real |

## What the platform asks of you

1. **A federated credential, no secret.** Your workflows sign in with `azure/login` and the OIDC secrets `AZURE_CLIENT_ID`, `AZURE_TENANT_ID` and `AZURE_SUBSCRIPTION_ID`, which `bootstrap consumer` sets. The credential trusts the **main** branch of your repository only.
2. **Resume before you deploy and pause after, always.** Your identity has a custom role **on the capacity itself** that reads, writes, suspends and resumes it (Azure requires the *write* permission to pause or resume). Do what `tools/cd.py` of the platform does: bound every step with a deadline, pause in a `finally` block, pause again in a last workflow step that signs in again, share the concurrency group `fabric-capacity`. Never leave the capacity running; the guard pauses it after at most 3 hours, which costs money.
3. **Do not resize or delete the capacity**, do not create another one, and do not touch the storage account. The role is on that one capacity, so it cannot create another and has no delete right; but because *write* is needed to pause and resume, it could technically resize that capacity: this is a rule you keep, not a barrier, and a resize changes the bill. The platform's own build refuses to run on a capacity of another size.
4. **After the platform is destroyed and rebuilt, ask the platform owner to run `bootstrap consumer` again**: the capacity is a new Azure resource, so the role assignment on it is gone.
5. **Never change a tenant-wide or capacity setting.** If something needs one, say which and where; a person does it.
6. **Synthetic data only**, no secrets in files, no tenant or subscription ids in files (they live in repository variables and secrets).
7. **Everything through pull requests.** Agents propose, humans approve.

## Variables your repository gets

`bootstrap consumer` copies these from the platform repository to yours. Use these names; they are the same names the platform's own tooling reads, so you can vendor `tools/cd.py` and its tests unchanged.

| Variable | Meaning |
|---|---|
| `CD_RESOURCE_GROUP` | The resource group that holds the capacity |
| `CD_CAPACITY` | The capacity name (also its name in Fabric) |
| `CD_LOCATION` | The region, for example `eastus2` |
| `CD_WORKSPACE_DEV`, `CD_WORKSPACE_PROD` | The workspace names |

Switch your own pipelines on with a variable of your own (`CD_ENABLED` is the convention); `bootstrap consumer` does not set it.

## Where things are, by name

| Thing | How to find it |
|---|---|
| Workspace id | `GET https://api.fabric.microsoft.com/v1/workspaces`, the one whose `displayName` is `CD_WORKSPACE_DEV` |
| Lakehouse and SQL endpoint | the workspace's items named `ContosoBankLH` (type Lakehouse) and its SQL analytics endpoint |
| Names of ontology, graph and semantic model the kit would create | `ContosoBankOntology`, `ContosoBankModel`; a content repository may use its own names |
| The tables | the 32 gold tables of the core tier, listed in `docs/generated/ontology-brief.md` of the platform repository and in the kit's `config` |

## What the content repository should contain

- **Prompts**, versioned, for the two outcomes: an end-to-end ontology and reports. Each prompt carries an id, a semver `version`, its inputs and acceptance checks, and every change adds a changelog line.
- **The ontology** as source (the entity and relationship spec, the TMDL and item folders generated from it) and **the reports** (Power BI PBIR, exported PDF/PNG). Generated files are regenerated by a tool, never hand-edited, and CI fails on drift.
- **CI**, offline and free: lint the prompts, validate the item definitions, run the unit tests, scan for secrets and personal data.
- **CD**, behind a switch and an approval: resume the capacity, deploy the semantic model, the ontology and the reports into the dev workspace, verify, **pause**; promote to prod after a manual approval.
- **A release** with a changelog, so each report and each ontology version can be traced to the prompt version that produced it.

## How a Part 2 repository is started

1. Create the repository (private), on a branch named by intent, through pull requests only.
2. Ask the owner of the platform to run `python -m tools.bootstrap consumer --repo <platform> --consumer <owner>/<content repo> --subscription <id> --execute` (it needs their go, and creates an Entra app, a role and secrets).
3. Run the platform workflow `build` once more so that the new identity becomes a capacity administrator and a workspace contributor.
4. Run your own pipeline's free checks first; a billable deployment only with the owner's explicit go.
